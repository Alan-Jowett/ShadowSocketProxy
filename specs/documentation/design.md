# ShadowSocketProxy Documentation Design

## Scope and impact map

| Requirement | Design | Validation | Implementation surfaces |
| --- | --- | --- | --- |
| REQ-DOC-001 | D-DOC-001, D-DOC-002 | TC-DOC-001, TC-DOC-002 | Rust source comments, rustdoc command, Rust coverage checker |
| REQ-DOC-002 | D-DOC-003 | TC-DOC-003 | BPF source comments, Doxygen configuration |
| REQ-DOC-003 | D-DOC-004 | TC-DOC-004 | Site template, documentation assembly |
| REQ-DOC-004 | D-DOC-005 | TC-DOC-005, TC-DOC-006 | GitHub Actions documentation validation job |
| REQ-DOC-005 | D-DOC-006 | TC-DOC-007, TC-DOC-008 | GitHub Actions publication job and `gh-pages` branch |

## Documentation generation

### D-DOC-001 — Rustdoc workspace generation

The workflow runs rustdoc for all workspace crates with private items enabled,
without compiling test-only documentation targets:

```text
cargo doc --workspace --no-deps --document-private-items
```

The generated workspace site is copied into the combined site under
`rustdoc/`. `RUSTDOCFLAGS="-D warnings"` makes rustdoc warnings visible
failures. Crate/module-level rustdoc documents platform scope, runtime
ownership, error semantics, and key invariants.

### D-DOC-002 — Rust coverage checking

A repository-owned checker examines in-scope non-test Rust sources and verifies
that each function and documented code element has a rustdoc comment. The
checker excludes `#[cfg(test)]` modules and `tests/` files, but includes
`build.rs` and the fixture-runner source. It fails with file/line diagnostics
for uncovered elements and runs before site assembly.

The checker is a documentation-quality gate only; it does not rewrite source
or infer behavior beyond identifying code elements and their preceding
rustdoc comments.

### D-DOC-003 — BPF Doxygen generation

The repository adds a pinned, warning-sensitive Doxygen configuration for the
canonical BPF source. The configuration:

- extracts documented and undocumented code elements needed for the BPF page;
- enables warnings for undocumented functions and members;
- uses the BPF source directory as the input scope;
- emits HTML under the combined site's `bpf/` directory;
- excludes generated objects, fixture binaries, and test code.

The BPF comments explain map ABI fields, packet bounds checks, IPv4/IPv6
rewrites, checksum updates, TCP lifecycle, UDP behavior, ingress/egress
entrypoints, and verifier constraints.

### D-DOC-004 — Combined site assembly

The documentation job creates a clean staging directory containing:

```text
site/
  index.html
  rustdoc/
  bpf/
```

The landing page links to the rustdoc index and BPF Doxygen index and states
the source revision used to generate the site. Site assembly starts from an
empty directory so stale pages cannot survive a later publication.

### D-DOC-005 — Pull-request validation

The existing CI workflow adds a documentation validation job triggered by the
existing pull-request and `main` push events. It installs Rust documentation
components and Doxygen, runs the Rust coverage checker, runs rustdoc, runs
Doxygen with warnings treated as failures, and assembles the combined site.

Pull-request execution has read-only repository contents permissions and does
not push branches or publish Pages content.

### D-DOC-006 — Main-branch orphan publication

After the same generation and validation steps succeed for a `main` push, a
publication step replaces the `gh-pages` branch with the staged site:

1. create an orphan `gh-pages` branch when absent;
2. remove all prior branch contents;
3. copy only the staged site;
4. commit the generated site with the source revision;
5. force-update `origin/gh-pages`.

The workflow grants only the repository contents permission required for this
push. Publication runs only when the event is a direct push to `main`; pull
requests never publish.

## Invariants

| ID | Invariant |
| --- | --- |
| INV-DOC-001 | Documentation generation never changes runtime, BPF ELF, map ABI, or test behavior. |
| INV-DOC-002 | Rust documentation is generated by rustdoc; BPF documentation is generated by Doxygen. |
| INV-DOC-003 | Test sources and generated test artifacts are excluded from coverage and publication. |
| INV-DOC-004 | Every generated site starts clean and contains only the combined documentation tree. |
| INV-DOC-005 | Only successful `main` pushes can update `gh-pages`; pull requests remain non-publishing. |
| INV-DOC-006 | The publication token cannot publish source files, secrets, or unrelated build artifacts. |

## Explicit no-impact decisions

- Existing Linux and Windows build/test jobs remain unchanged except for
  sharing the workflow's trigger scope.
- Rust and BPF runtime APIs, packet behavior, control-plane behavior, and
  host-proxy behavior are unchanged.
- The BPF Makefile's production ELF target remains unchanged.
- GitHub Pages repository settings are not managed by source; the workflow
  only maintains the `gh-pages` branch.
